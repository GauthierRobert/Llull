**Conclusion.** The architecture already has the right seams: commands, metaHistory, guards, document extensions, an audit
hook, and desktop hosts. What is missing is a PLM data model, its commands, a canonical hash, signatures, and a host-side
vault.

## 2. Target architecture

```
src/ui (PLM panel, lock overlay, release dialog)      desktop/ (vault host, keystore, file locks, package writer)
        │ dispatch(name, params)                              │ CLI `llull plm|vault|release …`   server/ (audit chain, shared vault V2)
        ▼                                                     ▼
src/app installDefaultPlugins() ── installs ──► packages/plm  (@plm)  CadPlugin { name:'plm', toolset:'plm',
                                                        commands, guards:[releaseLockGuard], document: plmExtension }

```

Laws check:

- **L1/L5.** Every capability is a registered command, so UI, CLI and MCP have parity.
- **L2.** Plugin → core public API only. Hosts do the I/O.
- **L3.** Pure: new `plm` objects, structural sharing.
- **L4.** `doc.plm` is mutated only by PLM commands.
- **L6.** The vault is host-side and no business logic lives in the server.
- **L8.** metaHistory, ids not step-scoped (PLM ids are user/business ids).
- **L9.** Kernel use is optional and goes through `ctx.kernel`.
- **L10.** Plugin.

## 3. Data model

```ts
// packages/plm/src/model.ts (type sketch). The document field is optional: absent = unmanaged document (no behaviour change).
export type LifecycleState = 'in_work' | 'in_review' | 'released' | 'superseded' | 'obsolete' | 'cancelled';
export type ItemType = 'part' | 'assembly' | 'drawing' | 'document';
export type RevisionSchemeId = 'asme-alpha' | 'numeric-2' | `custom:${string}`;
export type EffectivityKind = 'serial' | 'msn' | 'date' | 'lot';

export interface Effectivity {
  readonly kind: EffectivityKind;
  readonly from: number | string; // serial/msn: positive integer; date: ISO-8601 calendar date 'YYYY-MM-DD'; lot: string id
  readonly to?: number | string; // inclusive; absent = open-ended
}

export interface Approval {
  readonly role: string; // 'design-authority' | 'checker' | 'stress' | 'cm' | custom (policy-defined)
  readonly userId: string;
  readonly at: string; // host-supplied ISO-8601 UTC
  readonly comment?: string;
}

export interface SignatureRecord {
  readonly alg: 'Ed25519';
  readonly keyId: string; // vault key registry id
  readonly publicKey: string; // 64 hex chars (32 bytes)
  readonly meaning: 'authorship' | 'review' | 'approval' | 'release';
  readonly signer: { readonly userId: string; readonly name: string };
  readonly signedAt: string;
  readonly signedSha256: string; // SHA-256 of the exact signed bytes (canonical manifest)
  readonly signature: string; // 128 hex chars (64 bytes)
}

/** A revision is dirty when the current release-scope hash differs from its last iteration's contentHash (derived, never stored). */
export interface Iteration {
  readonly n: number; // 1-based; current iteration = iterations.length
  readonly contentHash: string; // release-scope SHA-256 at checkpoint
  readonly at: string;
  readonly by: string;
  readonly comment?: string;
}

export interface Revision {
  readonly label: string; // 'A', 'B', '01', …
  readonly state: LifecycleState;
  readonly basedOn?: string; // previous revision label
  readonly iterations: Iteration[]; // last = current iteration
  readonly changeOrder?: string; // ECO id that created / released it
  readonly effectivity: Effectivity[];
  readonly approvals: Approval[];
  readonly signatures: SignatureRecord[];
  readonly releasedAt?: string;
  readonly releasedBy?: string;
  readonly contentHash?: string; // frozen at release
  readonly snapshot?: ReleaseSnapshot; // definition at release (MVP inline; V1 externalized to vault)
  readonly geometryFingerprint?: GeometryFingerprint;
  readonly packageSha256?: string; // manifest hash once the host wrote the package (attach_release_package)
  readonly stateHistory: {
    readonly from: LifecycleState | null;
    readonly to: LifecycleState;
    readonly at: string;
    readonly by: string;
    readonly reason?: string;
  }[];
}

export type ReleaseSnapshot =
  | { readonly kind: 'inline'; readonly canonicalJson: string } // MVP: exact bytes that were hashed
  | { readonly kind: 'vault'; readonly objectSha256: string }; // V1: content-addressed object in the vault

export interface GeometryFingerprint {
  readonly kernel: string;
  readonly kernelVersion: string;
  readonly perEntity: Record<string, { volume?: number; area?: number; bbox: [number, number, number, number, number, number] }>;
}

export interface ManagedItem {
  readonly partNumber: string; // /^[A-Z0-9][A-Z0-9._\-\/]{0,63}$/i, unique in vault
  readonly name: string;
  readonly itemType: ItemType;
  readonly revisionScheme: RevisionSchemeId;
  readonly currentRevision: string; // working or latest revision label
  readonly revisions: Record<string, Revision>;
  readonly revisionOrder: string[];
  readonly marking: ExportMarking;
  readonly componentId?: string; // V1: sub-item bound to doc.components[componentId]
}

export interface ExportMarking {
  readonly regime: 'none' | 'undetermined' | 'ITAR' | 'EAR' | 'EU-dual-use' | 'national' | 'other';
  readonly classification?: string; // user text, e.g. ECCN or USML category (never computed)
  readonly statement?: string; // printed notice
  readonly decidedBy?: string;
  readonly decidedAt?: string;
}

export interface ChangeRecord {
  readonly id: string; // 'ECR-0002', 'ECO-0002' (user or generated)
  readonly kind: 'ecr' | 'eco';
  readonly title: string;
  readonly reason?: string;
  readonly affectedItems: string[]; // part numbers
  readonly purpose: 'initial-release' | 'change';
  readonly classification?: 'minor' | 'major'; // required when purpose = 'change'
  readonly classificationTags?: ('acoustical' | 'emissions')[]; // 14 CFR 21.93(b)(c) [R7]
  readonly classificationJustification?: string;
  readonly effectivity?: Effectivity[];
  readonly disposition?: { inStock?: Disposition; wip?: Disposition; fielded?: Disposition };
  readonly fromRequests?: string[];
  readonly state: 'open' | 'accepted' | 'rejected' | 'implemented' | 'cancelled';
  readonly notice?: string; // ECN id assigned when the ECO is implemented
  readonly createdAt: string;
  readonly createdBy: string;
  readonly closedAt?: string;
}
export type Disposition = 'use-as-is' | 'rework' | 'scrap' | 'return-to-supplier' | 'no-action';

export interface Baseline {
  readonly id: string;
  readonly name: string;
  readonly kind: 'functional' | 'allocated' | 'product' | 'custom'; // MIL-HDBK-61B vocabulary [R2]
  readonly members: { partNumber: string; revision: string; contentHash: string }[]; // sorted by partNumber
  readonly hash: string; // SHA-256(JCS(members))
  readonly at: string;
  readonly by: string;
}

export interface PlmPolicy {
  readonly requireChangeOrder: boolean; // default true after first release
  readonly requireIndependentChecker: boolean; // default true
  readonly requiredApprovalRoles: string[]; // default ['design-authority','checker']
  readonly humanSignatureRequired: boolean; // default true (agents cannot release)
  readonly requireMarking: boolean; // default false; true blocks submit while 'undetermined'
}

export interface PlmModel {
  readonly schema: 1;
  readonly item: ManagedItem; // MVP: one top item per document (assumption A-1)
  readonly subItems?: Record<string, ManagedItem>; // V1: keyed by partNumber, bound to components
  readonly changes: Record<string, ChangeRecord>;
  readonly changeOrder: string[];
  readonly baselines: Record<string, Baseline>;
  readonly asBuilt?: Record<string, AsBuiltRecord>; // V2, keyed by serial
  readonly characteristics?: Record<string, Characteristic>; // V1 (gap 03)
  readonly policy: PlmPolicy;
}

export interface AsBuiltRecord {
  readonly serial: string;
  readonly partNumber: string;
  readonly asDesignedBaseline: string;
  readonly deviations: { partNumber: string; installedRevision: string; authority: string }[];
  readonly at: string;
  readonly by: string;
}

export interface Characteristic {
  // balloon; stable id independent of PMI entity id churn
  readonly charNo: number;
  readonly sourceRef: { readonly kind: 'dimension' | 'gdt' | 'note' | 'material' | 'process'; readonly id: string };
  readonly sheetId: string;
  readonly zone?: string;
  readonly designator?: string;
  readonly requirementText: string; // rendered exactly as on the drawing
  readonly introducedIn: string; // revision label
  readonly retiredIn?: string;
}
```

## 5. Algorithms

### 5.1 Release scope & content hash (TR-PLM-17, FR-PLM-06/15/16)

1. `scope(doc) = { format:'llull-document', version, document: omit(doc, ['selection','camera','plm']) }`, with derived
   entities **omitted** (`includeDerived: false`, i.e. exactly what a saved file stores). Plugin-derived geometry (L8) is
   regenerated from the definition by plugin code; hashing it would make the release hash change on a llull/plugin upgrade
   and raise false integrity mismatches. Derived geometry is covered instead by `geometryFingerprint` (volume, area, bbox per
   entity, derived entities included), whose drift is reported, never treated as tampering (R-2).
2. `canonical(x)`: RFC 8785 profile [R16]:
   - objects get keys sorted by UTF-16 code units;
   - no whitespace;
   - strings serialized with the ECMAScript `JSON.stringify` escaping;
   - numbers serialized with `Number.prototype.toString` (JCS uses the ECMAScript algorithm);
   - `-0` → `0`;
   - non-finite values refused (llull validation already rejects them);
   - `undefined` properties omitted, as in JSON.
3. `contentHash = hex(SHA-256(UTF-8(canonical(scope(doc)))))` (FIPS 180-4 [R17]).
4. Golden vectors: `validation/vectors/hash_vectors.json`:
   - sample document scope hash `7e3943fb…f3c24f` over 1551 bytes;
   - invariance under camera/selection change and key reordering;
   - sensitivity to a parameter edit `c913cadc…91017e`;
   - cross-checked in Python and Node.
5. Unicode: no NFC normalization (bytes as authored). Part numbers are restricted to ASCII by regex, which avoids the
   main normalization trap.

### 5.2 Release lock guard (TR-PLM-18, FR-PLM-05)

The decision uses **both** documents, so that one transaction (`build_project`, which the guard also sees as a whole) may
`revise_item` and then edit the new revision, while nothing can edit a locked revision:

```
check(prev, next, commandName):
  if commandName in {'load_document','clear_document'} → null          // replacement; integrity handled on load (5.5, TR-PLM-33)
  if prev.plm?.item is absent → null                                   // unmanaged before the change
  if next.plm?.item is absent → 'the PLM record cannot be removed'      // only load/clear may drop it
  if !scopeChanged(prev, next) → null                                  // PLM-only or view-state change
  for every revision label L in prev.plm.item.revisions:               // released history is immutable
      if next.plm.item.revisions[L] differs from prev in state (other than the transitions of
         lifecycle_transitions.csv), contentHash or snapshot → return `… rev ${L} history cannot change`
  cur = next.plm.item.revisions[next.plm.item.currentRevision]
  if cur.state in {'in_work','cancelled'} and (cur.label === prev current label or cur.basedOn === prev current label
         and prev current revision is released)                       // edit of the open revision, or revise-then-edit
      → null
  return `${item.partNumber} rev ${cur.label} is ${cur.state}; open an ECO and revise_item`
scopeChanged(prev, next) = some key K of RELEASE_SCOPE_KEYS (every CadDocument key except selection, camera, plm, plus
                            plugin slices) with prev[K] !== next[K]
```

A non-PLM command cannot create a new in_work revision (only PLM commands write `plm`, and `plm` changes inside the same
result are themselves checked by the history loop above), so "next is in_work" cannot be forged by an ordinary command.
The check costs O(number of top-level keys + revisions), about 30 reference comparisons, so it stays well under the 1 ms
budget, thanks to structural sharing (L3). False positives would come from a command that re-creates an unchanged top-level
object. Mitigation: the contract test runs every registered mutating command on a released document and asserts either
refusal or `next[key] === prev[key]` for all scope keys (TR-PLM-30). A second contract case runs a `build_project` with
`revise_item` + `set_parameter` on a released document and expects success.

### 5.3 Revision schemes (FR-PLM-02)

`asme-alpha`:

- alphabet = A–Z minus {I,O,Q,S,X,Z}, 20 letters (secondary source [R26]);
- label(n) = alphabet[n-1] for n ≤ 20;
- else alphabet[(n-21) div 20] + alphabet[(n-21) mod 20];
- capacity 420.

`numeric-2`: zero-padded. `custom:<name>`: an ordered list stored in policy. Vectors: `vectors/revision_sequence.json`
(J = 9th, P = 14th, Y = 20th, AA = 21st, YY = 420th).

### 5.4 Diff (FR-PLM-13)

Both sides are canonical scope objects. The diff is computed per category:

- `parameters`: by name, comparing expression;
- `featureHistory`: LCS on `(name, canonical(params))` with step ids as anchors, giving added/removed/edited/suppressed;
- `entities`: by id, giving added/removed/changed kinds;
- `materials`, `components`, `drawings.sheets[*].titleBlock`;
- effectivity.

Optional geometry: per-entity volume/area/bbox delta via `ctx.kernel` (OCC `BRepGProp` mass properties on desktop).
Tolerance: relative 1e-9 on volume for "unchanged" (same kernel). Across kernel versions a relative 1e-6 drift is reported
as drift, not as a change.

### 5.5 Integrity on load (FR-PLM-15)

`plmExtension.validate` cannot hash (validation is structural) and `restore` sees the raw, unvalidated document and cannot
report anything. The check therefore runs in the new `afterLoad(doc)` hook (TR-PLM-33), on the validated document, and
recomputes:

- `contentHash` of the **current** scope when the current revision is released;
- the snapshot hash of every released revision.

A mismatch is returned as a warning string that `load_document` appends to its summary:
`release A content hash mismatch (expected 7e39…, got …)`. Because `afterLoad` cannot modify the document, the mismatch
state is not stored: `plm_status` and `verify_release` recompute it on demand (`data.integrity`), and the revision stays
locked (the guard never unlocks a released revision). The fix is to revert to the snapshot (`restore_revision_snapshot`, a
mutating command allowed only while the recomputed hash mismatches) or to open an ECO.

### 5.6 Effectivity (FR-PLM-11/12)

- Ranges are inclusive. Serial/MSN are integers; ISO dates are compared lexicographically (`YYYY-MM-DD`).
- On release of N+1 with cut-in `from = f`, each open range of N of the same kind closes at `f-1` (integer) or the previous
  calendar day (date, computed with pure date arithmetic and no clock).
- Overlap between released revisions of the same kind is refused.
- `resolve(kind, unit)` = the first released/superseded revision whose range contains the unit.
- Obsolete revisions keep their history but are excluded from resolution.

Vectors: `vectors/effectivity_resolution.json`.

### 5.7 Signatures (FR-PLM-20)

- Algorithm: Ed25519 PureEdDSA (RFC 8032 [R15]; approved in FIPS 186-5 [R18]).
- Signed bytes: `UTF-8(canonical(manifestBody))`, where `manifestBody` is the manifest without `manifestSha256` and
  `signatures`.
- Deterministic: the same key and bytes always give the same signature, which makes golden tests possible (the sample
  manifest is signed with the public RFC 8032 TEST 1 key: `78343a41…1b5f460c`).
- Key custody (host): private keys stay in the OS keystore or a hardware token. The desktop uses Electron's OS-backed
  secret storage to protect a locally generated key (candidate API, to verify), or PKCS#11 tokens in V2.
- Public keys are registered in `vault/keys/<userId>.json` with validity dates. Revocation is a signed vault entry.
- The trust store **must reject** the RFC 8032 test public keys (`d75a98…511a`, `3d4017…660c`, `fc51cd…8025`) outside test
  mode (TR-PLM-19).

### 5.8 Audit chain (FR-PLM-19)

`server/src/audit.ts` keeps its format and adds:

- `prevSha256`;
- `entrySha256 = sha256(canonical(entry without entrySha256))`;
- `paramsSha256` computed with `canonical`, not `JSON.stringify`.

Vault mode disables deletion on rotation: rotated segments are moved to `vault/audit/` and the chain continues across
files. On desktop, the same writer runs in the backend process (KI6 starts the server bundle, so it is already present).
Verification: `llull audit verify <dir>` recomputes the chain.

| Option                                                           | Pros                                                                                          | Cons                                                                                                               | Decision                |

- **Check-out** = create the lock with `O_CREAT|O_EXCL`, then load the head into the app via `load_document`.
- **Check-in** = `checkpoint_iteration` (command), write the head blob, update `refs.json` atomically (write tmp + rename),

- Lease 8 h, renewed every 10 min while the app runs.
- A stale lock (lease expired and pid absent on the same host) can be broken by its holder or by the CM role. Breaking is
  audited.
- Read-only open never locks.

### 13.5 Threat model (what this does and does not protect)

| Topic                                       | Protects                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | Does not protect                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Human gate                                  | An agent that reaches llull only through commands, the CLI or REST cannot approve, release, classify, mark or accept: it holds no trusted key. A signature binds one act, one set of params, one PLM state and (release, approval, marking) the content hash of the definition; PMI review binds a hash of the reviewed items; it is single-use (spent in the trust directory). The host clock stamps gated acts.                                                                                            | Code running as the same OS user with file access can read an enrolled key file and brute-force or watch the passphrase, and can read `trust.secret`. The desktop confirmation separates agent-reachable surfaces from the user; it is not a defence against arbitrary code with the user's file access.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Trust store                                 | A key counts only after a native desktop dialog (`TrustGrant` issued only by `desktop/`, enforced by dependency-cruiser); the location is fixed per user profile and NO environment variable can move it (an agent controls its process environment, so `TEST=true`, `VITEST`, `LLULL_TRUST_DIR` and `LLULL_PLM_TEST_KEYS` do nothing: attack tests in `plmCli.test.ts`, `plmSigning.test.ts`); an edited `trust.json` (HMAC under `trust.secret`) trusts nothing; revoking from the CLI only reduces trust. | Whoever holds `trust.secret` can re-sign the file. The grant is a structural proof, not a capability the type system seals.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| Release lock                                | Every command that changes the definition of a released / in-review revision is refused (guard, contract test over the registry); history of released revisions is immutable inside the document.                                                                                                                                                                                                                                                                                                            | It is **advisory**: `load_document` / `clear_document` replace the whole document, and anyone can edit the saved file or run an older build. Integrity is then DETECTED on load (`afterLoad`, `plm_status`, `verify_release`, content hash and snapshot) but not prevented; `restore_revision_snapshot` repairs.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Signatures                                  | A release signature covers the canonical release manifest (item, state at release, change, effectivity, marking, release stamp, content hash, tool, unverified flags, **meaning**); the content hash covers the whole definition; the package manifest hash (recorded by the human-signed `attach_release_package`) covers every member.                                                                                                                                                                     | A signature does not cover the drawings by itself (only through the package manifest hash), says nothing about the correctness of the design, and a stolen unlocked key signs anything. Test keys are published secrets.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Audit chain                                 | Detects an edited, removed (middle), reordered or half-written line; survives rotation and a crash (a torn line is closed by an `audit_chain_break` entry); two processes share one chain under a lock file.                                                                                                                                                                                                                                                                                                 | The chain is UNKEYED: whoever can write the directory can rewrite the whole chain consistently or cut its tail. Anchor the head hash outside the machine to detect that (V2).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Package                                     | Members and manifest are re-hashed, paths cannot leave the folder, a package with no signature is not `ok`, signatures are re-verified against the trust store.                                                                                                                                                                                                                                                                                                                                              | A package verified on a machine whose trust store is empty reports `PLM_KEY_UNTRUSTED`: trust is local by design (offline, AF-41).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Package anchor                              | The package manifest hash must equal the value a human attached (`attach_release_package` is a signed act) or an out-of-band hash: a swapped drawing with every member hash, the manifest hash and the release signature recomputed is caught (attack test in `plmReleasePackage.test.ts`).                                                                                                                                                                                                                  | The anchor read from `--doc` is only as trustworthy as that document file, which an agent can edit: for an adversarial check pass `--manifest-sha256` received from the releasing human.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Signing passphrase                          | Read only at an interactive no-echo terminal prompt (CLI) or typed in the desktop dialog; never from the environment, a flag or stdin; the signing endpoint counts failures per key, persists them and doubles the lock after four (429).                                                                                                                                                                                                                                                                    | A process that can read the terminal (same user, a debugger, a keylogger) sees it; whoever can write the trust directory can reset the counter.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Key trust dialog                            | Shows the owner, creation time and fingerprint, and warns when the owner already has a trusted key or several keys are pending.                                                                                                                                                                                                                                                                                                                                                                              | The user still decides from what the key store claims: an agent can enroll a key under a name the user knows and hope for a click. Confirm only a key you enrolled yourself in the last minutes.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Same-user code (the main unprotected class) | The gate is a GUARD-RAIL against agents that use llull's commands, CLI or REST: they hold no trusted key and no passphrase.                                                                                                                                                                                                                                                                                                                                                                                  | It is NOT a security boundary against arbitrary code running as the same OS user (a shell-capable agent): it can read key files and attack the passphrase offline (the signing lock only slows guessing through the endpoint), delete `consumed.txt` (single-use holds only while it exists), read `trust.secret`, or drive the terminal. A TTY is not proof of a human: the prompt therefore prints the act, the part number and the content hash it signs. A replay can only repeat the same act on the same state and content. The real boundary would be a Windows Hello / TPM-held key reached through the native sidecar (future item).                                                                                                                                                                                                                                                                                                                                                  |
| CLI signing                                 | The CLI does not trust its backend (`--server` or `~/.llull/desktop.json` are agent-writable): for a gate it checks the backend's `plm_act_payload` answer is `plm:<command>` with exactly the user's params, rebuilds the payload hash LOCALLY (`humanGatePayload`) and signs only that; `release sign` checks the returned manifest is the revision and meaning asked for. A hostile backend returning another act's hash is refused (`plmCli.test.ts`).                                                   | The state and content hashes inside the details come from the backend (the CLI has no document of the live app): they are shown to the user before the prompt, not verified.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Trust file root key                         | `trust.json` is HMAC'd under `trust.secret`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | Anyone who can read `trust.secret` can forge trust. Signing `trust.json` with an owner root Ed25519 key whose passphrase is typed in the desktop trust dialog is NOT built (cost: a second key hierarchy and a recovery path); it would make forging trust need that passphrase, not just file access. Documented, future item.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Backend port                                | The desktop accepts the backend only if `/health?challenge=N` answers HMAC(token, N) (`healthChallenge.test.ts`): a process that took the port between probing it and the fork is refused.                                                                                                                                                                                                                                                                                                                   | The CLI's `--app` discovery still reads `desktop.json` (agent-writable) and its bearer token; mitigated for signing by CLI signing above.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Dispose acts (05 / 04 / 21)                 | Each is a verified signature by a trusted key, single-use; `dispose_fit_result` can re-run `fit_at_temperature` itself (`fitParams`) and requires the recomputed row to hash to `inputsHash`; its payload carries the act name.                                                                                                                                                                                                                                                                              | The signing endpoint cannot recompute analysis rows, so for `dispose_margin`, `dispose_thermal_limit`, `dispose_fit_result` and `set_review_disposition` the payload comes from the client (an allow-listed act, audited): a compromised renderer could show one row and sign another. The signed command still verifies the payload against the data it holds.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Local vault                                 | Concurrent sessions cannot hold one item (`O_EXCL`, lease, holder named); objects are immutable and re-hashed on read, so a damaged or swapped object is found (`llull vault verify`, `verify_release`); check-in refuses a document whose frozen revision differs from the vault record; every check-out, check-in, renew and lock break is in the hash-chained vault audit log.                                                                                                                            | One machine, one OS user: anyone who can write the vault folder can rewrite objects, refs, locks and the (unkeyed) audit chain consistently, or delete an object (the document then reads `PLM_VAULT_OBJECT_MISSING` / integrity `mismatch`; a release package is the offline copy). A lock is advisory outside llull (no authenticated role: any user of the folder can break a stale lock; the break is audited). The vault is not a backup. The vault location is $LLULL_VAULT (agent-controlled): a swapped or relocated vault cannot inject content, because every object is named by its SHA-256 and re-hashed on read (a mismatch reads as absent), the revision keeps `objectSha256 === contentHash`, and `restore_revision_snapshot`, `verify_release`, `view_revision` and the package writer refuse (or report PLM_VAULT_OBJECT_MISSING) when the object is absent or damaged (`vaultSnapshot.test.ts`, `plmVault.test.ts`). A swapped vault can only withhold (denial), not forge. |
| Sub-item binding                            | `bind_component_item` is a human act (signed over the exact params and the PLM state, through the same single-use confirmation path as every PLM act), so an agent cannot declare a child released or change the structure of a released assembly (only in_work); the structure is frozen into the release (`releasedStructure`, in the signed manifest) and baselines are hash-checked on load.                                                                                                             | The state and hash of a child are the signer's attestation: llull does not read the child's own document or vault from here, so a wrong attestation by a trusted human is not detected (shared vault, M6).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Plm slice on load | `plmDocument.validate` checks the shape (not only the seal) of every as-built record, MBOM and result set, and seals result sets like the others; ids that are `Object.prototype` members are not entries (`own`). | A syntactically valid, consistently re-sealed edit of a file is indistinguishable from the original (the seal is not keyed). |
| As-built records and MBOMs                 | `record_as_built` is a human act over its exact params (an agent cannot declare a unit conforming or waive a deviation); records and MBOMs carry a SHA-256 seal checked on load and on every read, and no command edits or removes one. | The signer attests what is installed: llull cannot see the unit. The seal is not keyed: someone who edits the file can recompute it (the PLM state hash that every later human signature covers changes, so later acts do not carry over, but the record itself is only as trustworthy as the file). A wrong record cannot be corrected in place (13.3). |
| QIF results import                         | The XML reader refuses DOCTYPE, ENTITY and processing instructions, so there is nothing to expand or load (no XXE, no entity blow-up); size, nesting, element and attribute counts are capped while reading; no recursion; work proportional to the input (tests with 2 to 7 MB hostile shapes), no recursion. The import is a human act over the exact params, file text included, and keeps the file SHA-256, so an agent cannot enter passing results and a later file swap is visible. | The signer signs a hash of the params: they must know which file it is (compare the file hash printed in the summary). The measuring system's status is stored as written and not re-judged; the item-name to balloon-number mapping is a convention. A malicious but well-formed QIF from a trusted human is accepted. The reader is not a validating parser (no XSD check). |
| AP242 PDM export                           | Read-only data; the writer escapes every string and an independent reader compares the file with the model (a red check exports nothing); behind the 08 export-control gate for controlled materials. | The file is data, not authority: signatures inside it prove nothing unless verified (`llull release verify`). The item export marking travels as a SECURITY_CLASSIFICATION entity but does not by itself require the human confirmation (only controlled MATERIALS do, 08). The id owner organization defaults to a placeholder unless the caller sets it. |
| LOTAR package                              | Everything the release package protects (13.5 Package, Package anchor), plus: the validation properties are re-derived from the archived definition on verify, the PDM file is read back and compared with the manifest, and sealed records are re-checked. A forged archive whose validation properties, member hashes and manifest hash were all recomputed is caught by the anchor, and without the anchor by the re-derivation (attack test in `plmLotar.test.ts`). | The validation properties are computed by the same code that wrote the archive, so a bug there is archived with the data; the re-derivation catches inconsistency, not a wrong algorithm. Without the human-attached anchor (or one received out of band) the verdict is not ok. The package holds llull's native format: long-term retrieval depends on llull or on reading the documented JSON. No claim of EN 9300 conformance (13.3). Export-controlled content is archived only with the human confirmation. |
