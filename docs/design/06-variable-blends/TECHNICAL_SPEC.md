### 2.2 Data flow

```
CLI / UI ──execute──> fillet_edge {id, edges[law], profile, corners}
   core: resolve edges / vertices by name | point (SC-N1) → validate laws (geometry/blend/law.ts) → expression → samples
         → recipe { op:'fillet', source, edges, radii, profile?, corners? } → ctx.kernel.evaluate(recipe)
   native: MakeFillet (circular, rails) → [profile ≠ circular] replace blend faces keeping rails → [setback] trim + N-sided fill
           → BRepCheck → named shape | null + BlendReport
   core: null → ctx.kernel.blendReport(recipe) → BLD_* code + ids + remediation (probe hint) ; ok → mesh entity { brep: recipe }
check_blends → ctx.kernel.faceQuery.blendInfo(shape) + edgeContinuity(contact edges) → data { blends[], findings[] }
```

### 2.3 Laws check

- L1/L5: every capability is a registered command; `probe_fillet` and `check_blends` are queries (`readOnly`, `data`).
- L3: commands return a new document; laws stored as given (expressions as text, not as sampled arrays).
- L8: params are design intent (radii, fractions, rho, shape factor, setback lengths, expressions, face / edge / vertex names and
  points). Sampling of an expression law happens at evaluation, deterministically (fixed `samples`, uniform `t`).
- L9: all construction through `ctx.kernel`; `requiresKernel: true` on the four mutating commands; Manifold refuses.
- L2: `geometry/blend/*` is pure math (no DOM, no fetch); native code lives in `solver/`.
- No tension found that needs the owner (W6).

## 5. Kernel / algorithms

### 5.1 Radius laws (core `geometry/blend/law.ts`, native `blends.cxx`)

| Law                    | Core validation                                                                                                         | Native construction                                                                                                            |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------- | ------------------------------------------------ |
| constant               | `size > 0`                                                                                                              | `Add(r, E)`                                                                                                                    |
| start → end            | both > 0                                                                                                                | `Add(r1, r2, E)`                                                                                                               |
| control points, smooth | `t` strictly increasing in (0, 1), sizes > 0                                                                            | `Add(UandR, E)` (today)                                                                                                        |
| control points, linear | same                                                                                                                    | `Add(Law_Composite of Law_Linear pieces, E)`                                                                                   |
| expression             | parses with `lib/expression.ts` (variable `t` only + document parameters), finite > 0 at every sample, `samples` 5..257 | sampled at `t_k = k/(n-1)` → `UandR`                                                                                           |
| closed chain           | `                                                                                                                       | r(0) − r(1)                                                                                                                    | ≤ 1e-9 × size`else`BLD_LAW_NOT_PERIODIC` | periodic interpolation (`Law_Interpol` periodic) |
| `over: 'chain'`        | —                                                                                                                       | `t` is the relative abscissa on the contour (OCCT `RelativeAbscissa`); `over: 'edge'` maps a per-edge `t` into the chain range |

Geometric facts used by the VCs (derived in `validation/generate_blend_refs.mjs`): on two planes meeting at interior angle α the
contact lines lie at `t = r cot(α/2)` from the edge — for **both** the section construction and the rolling-ball envelope (the
sphere of radius r centred r from a plane touches it at the foot point, which satisfies the characteristic condition), so planar
face areas are construction-independent; the removed volume is `∫ A(r(s)) ds` with `A(r) = r²[cot(α/2) − (π − α)/2]` for the
section construction. For a linear law of slope 0.05 the envelope removes 0.08 % less at mid-span, for slope 0.1 the total removed
differs by 0.33 % (`data/variable_radius_laws.json`, `data/extra_cases.json`); VC-BLD-30 tells which one the kernel builds.

### 5.2 Chord on curved faces (core + native)

Planar pair: closed form (today). Curved pair: per sample `s` the native code intersects the section plane (normal to the edge) with
both faces, takes the tangent lines at the edge point, computes the local wedge angle `α(s)` and `r(s) = c(s) / (2 cos(α(s)/2))`,
then builds a law (`UandR`, ≥ 17 samples) — exact for a cylinder rim against its cap (meridian sections are two perpendicular
lines: VC-BLD-06). Refuse with `BLD_CHORD_UNDEFINED` where `α(s) ∉ (0, π)` (tangent faces).

### 5.3 Profiles: section curves

In the section plane at spine point `s`: contact points `A` (on face 1), `B` (on face 2), unit tangents `u1`, `u2` of the face
sections pointing **towards** the corner, their intersection `T` (planar faces: the edge point).

| Profile            | Section                                                                                                                                                                                                                                                         | Continuity                         | Closed-form checks                                                                                                                                                                                                                                                                                          |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------- | ------------------------------ | ----- | ---------------------- | -------------------------------- | -------------------------------------------------------------------------------------- |
| circular           | arc tangent at A, B                                                                                                                                                                                                                                             | G1 (curvature jump 1/r: VC-BLD-10) | `A(r)` above                                                                                                                                                                                                                                                                                                |

Sizing of non-circular profiles by `radius`: the contact lines are those of the circular fillet of that radius (tangent distance
`r cot(α/2)`), so rails, topology and corner extents are identical to the circular case.

### 5.4 Profile replacement (native `blend_profile.cxx`) — "keep the rails, change the section"

1. Build the circular fillet with `BRepFilletAPI_MakeFillet` (same laws) → result shape, `NewFaces(I)` per contour, contact edges
   (shared edges between blend faces and support faces), spine = the input edge chain.
2. For each blend face: sample `s` along the spine (adaptive, ≥ 33 sections, chord tolerance 1e-4 × r), compute section curves
   (§5.3) from the support faces' local geometry (`BRepLProp_SLProps` at the contact points), build a B-spline surface through the
   sections (`GeomFill_Generator`-style skinning with rails as `u = 0, 1` iso-curves forced to the existing contact edges'
   3D curves; tolerance 1e-6 × bbox, max degree 8) — the Hartmann-style G^n blend on rolling-ball contact curves (R14).
3. Replace the face's surface, keeping its edges (`BRepBuilderAPI_MakeFace(surface, wire of the old edges)` + `ShapeFix_Face`),
   substitute with `BRepTools_ReShape`; corner patches touching replaced faces are rebuilt by `BRepOffsetAPI_MakeFilling` (G1 to
   all neighbours; G2 COULD).
4. `BRepCheck_Analyzer`; names: the replaced face keeps `blend(<edge>)`, corner patches keep `blend(v:…)` (naming.hxx roles).
5. Failure ⇒ `BLD_PROFILE_FAILED` with the face and section index.

### 5.5 Setback corners (native `blend_corner.cxx`)

1. Build the circular / profiled fillets with **no** corner patches at the setback vertices: trim each incident blend face at the
   section plane through the point at distance `s_i` from the vertex along edge `i` (`BRepAlgoAPI_Splitter` with a plane tool;
   remove the vertex-side piece and OCCT's corner patch).
2. The hole is bounded by the trimmed blend edges and the support face edges between the setback sections; fill it with
   `BRepOffsetAPI_MakeFilling` (boundary edges G1 to their faces, `Degree 3`, `NbPtsOnCur 15`, `NbIter 2`, `Tol3d 1e-4`,
   `TolAng 0.01`), sew (`BRepBuilderAPI_Sewing`, 1e-6 × bbox) and solidify.
3. A vertex of ≥ 4 blended edges: same path (OCCT's own patch is never attempted there).
4. Checks: `s_i ≥ t_i` (tangent distance of edge `i` at the vertex) else `BLD_SETBACK_TOO_SHORT`; fill G1 achieved ≤ 0.01 rad
   (reported) else `BLD_CORNER_FAILED`.
5. VC invariants: an edge's cylindrical blend face spans `L − s_start − s_end` (VC-BLD-12).

### 5.6 Face-face fillets, hold lines, full round (native `blends.cxx`)

| Feature                   | Algorithm                                                                                                                                                                                                                                                                                                                                                                                                                                                             | Notes                                                                       |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `fillet_faces` constant r | offset face sets A, B by r towards the material (`BRepOffsetAPI_MakeOffsetShape` per face / `Geom_OffsetSurface`), intersect → spine (`BRepAlgoAPI_Section`), project spine on A and B → rails (`GeomAPI_ProjectPointOnSurf` sampled + `GeomAPI_PointsToBSpline`), surface `GeomFill_Pipe(spine, railA, railB, r)` (R1); split A and B along the rails (`BRepFeat_SplitShape` / `BRepAlgoAPI_Splitter`), remove the faces between the rails (consumed), sew, solidify | two faces only ⇒ `FilletSurf_Builder` is an alternative section engine (R1) |
| variable r / width        | sections built per spine sample (§5.3) instead of `GeomFill_Pipe`                                                                                                                                                                                                                                                                                                                                                                                                     | as §5.4 step 2                                                              |
| no solution               | offset surfaces do not intersect, or the blend leaves the material (planar check: `r (√2 − 1) ≥ c/√2` across a chamfer of leg c, `data/face_fillets.json`)                                                                                                                                                                                                                                                                                                            | `BLD_FACE_FILLET_NO_SOLUTION` + minimum radius when known                   |
| hold line                 | planar faces at constant wedge α: core converts the hold curve's distance `h(s)` to the edge into `r(s) = h(s) tan(α/2)` and calls the edge path (exact, VC-BLD-17); otherwise native: rail A = the hold curve, rail B from the section circle tangent to face A at the hold point and to face B                                                                                                                                                                      |                                                                             |

### 5.7 Chamfer variants (native)

`Add(D1, D2, E, F)` with `F` = face `side1`; `AddDA(D, Angle, E, F)` with the angle in radians on `F`. Distance-angle second leg on a
wedge α: `d2 = d sin φ / sin(π − α − φ)` (VC-BLD-18: 90°, d 1, 30° ⇒ 0.577350). Variable chamfer (COULD): no OCCT law ⇒ section
construction like §5.4 with a straight section.

### 5.8 Diagnostics (native → core)

After a failed `Build`: for each contour `StripeStatus(IC)`, `NbFaultyContours`, `FaultyVertex`, `HasResult`; before `Build`: vertex
valence of contour ends (≥ 4 ⇒ unsupported). The worker keeps the report of the last failed evaluation per `recipeKey`
(`blendReport(recipe)`), so core can explain a null without a second build. Core maps it (§7.1) and, for `BLD_RADIUS_TOO_LARGE`,
runs at most 8 extra evaluations to put the largest working radius in the remediation (same bisection as `probe_fillet`, cached).

### 5.9 Native queries needed by `check_blends`

Implement the null answers in `bins/llull-kernel/src/queries.rs`: `faceQuery.edgeSamples` (points, tangents along an edge) and
`faceQuery.edgeContinuity` (per sample: G0 gap, G1 angle between the two faces' normals, normal curvatures of both faces across
the edge — `BRepLProp_SLProps` on each face at the edge point's `(u, v)`, curvature in the direction normal to the edge in the
tangent plane), plus `faceQuery.blendInfo` (blend faces by name role `blend(…)`, contact edges, section circle fit at `t`:
three points of the iso-curve across the face → radius; for non-circular profiles the curvature at the section midpoint is reported
as `midCurvature` instead of a radius).

### 13.2 Behaviour that differs from the sketch above

- `edgeSamples(shape, edge, count)`: `count` in 2..1001 uniform parameter samples (`t` 0..1, arc length `s`, point, unit tangent along the edge parametrisation, curvature, `dCurvatureDs` by central difference, torsion, principal normal). `edgeContinuity`: for an edge shared by exactly two distinct faces, `g0` = distance between the two faces' points at the shared pcurve parameter, `g1` = angle between the two outward normals (0 = tangent, pi/2 = box edge), `normalCurvature` = the curvature of each face in the tangent-plane direction normal to the edge (`k1 cos² + k2 sin²`), signed against the outward normal; null for boundary, seam or non-manifold edges. A circular fillet against a plane gives `[0, 1/r]`.
- `blendReport` stage is `contours | corners | validity | none` (`none` = the fillet builds); extra fields `done`, `valid`, `message`. Core maps `startsol_failure` to `BLD_RADIUS_TOO_LARGE`, `walking_failure` to `BLD_WALKING_FAILURE`, `twisted_surface` to `BLD_TWISTED_SURFACE`, a generic `error` or an invalid / vertex-less result to `BLD_INVALID_RESULT`, a faulty vertex to `BLD_CORNER_UNSUPPORTED` when 4 or more edges meet there, else `BLD_CORNER_FAILED`. `BLD_CORNER_UNSUPPORTED` is never raised from the pre-Build valence alone (VC-BLD-13).
- Refusals are `rejected` with `error { code, ids: [entity], paths: ['radius' or 'edges'], remediation }`; for `BLD_RADIUS_TOO_LARGE` the summary adds "largest that builds: X mm" from at most 8 extra evaluations (all requested sizes scaled together; 1/128 resolution). A kernel without `blendReport`, a report that finds nothing wrong, or a chamfer / shell keep the generic summary.
- `probe_fillet`: per edge, constant radius; the first guess `upperBound` = least mean width (`face area / edge length`) of the adjacent faces is NOT a bound (a cylinder rim R 10 H 50 gives 5 but accepts 10), so a guess that builds is doubled up to the bounding-box diagonal until a radius is refused, then bisected (measured rim: maxRadius 10, `BLD_INVALID_RESULT` beyond, 11 evaluations); default tolerance 1e-3 x bounding-box diagonal (1e-3 x the guess when the diagonal is unknown; named `probeTolerance`), default 12 evaluations, at most 32 edges per call; edges are probed alone (interactions are not probed).
- `check_blends` v1: edge blends only (faces named `blend(e(A|B))`); a contact line is an edge between a blend face and one of its two support faces `A`, `B` (so the end-wall edges of a blend are not contacts). Per contact: `g0Gap`, `g1AngleRad`, `g2Gap`, `g2Rel`, `order`. A blend face with no measurable contact (kernel returned null, or no edge matches its supports) gives `BLD_CHECK_UNVERIFIED_CONTACT` (warn, added) instead of a pass; with nothing to check (no filleted solid, `ids: []`) the status is `not_run`. The gap tolerance is computed per solid (1e-6 x its diagonal) and a gap above it rates the contact order `none`. Findings: `BLD_CHECK_G1_ANGLE`, `BLD_CHECK_G2_JUMP` (fail with `require: G2`, else info), `BLD_CHECK_INVALID`, `BLD_CHECK_UNVERIFIED_PICK` (no names), with `purpose: release` `BLD_CHECK_TOLERANCE_DEFAULTED` and `BLD_CHECK_REVIEW`; plus `BLD_CHECK_G0_GAP` (added: §7.1 had no code for a gap). Not in v1 (they need `blendInfo`, M1): `radius {min, max, at}`, `BLD_CHECK_RADIUS_LAW`, `BLD_CHECK_THIN_WALL`, corner patches (`kind: 'corner'`).

### 13.7 Behaviour that differs from the sketch (DES-6b)

- **OCCT facts found while building** (read from `ChFiDS_FilSpine.cxx`, 7.9.2): (1) `BRepFilletAPI_MakeFillet::Add(Law_Function, E)` is unusable: `ChFiDS_FilSpine::SetRadius(Law_Function)` builds a `Law_Composite` and discards it, so `Build` finds no radius and crashes (an access violation, not a `Standard_Failure`). (2) Every evolving radius ((r1, r2) or `UandR` points) is a cubic `Law_Interpol` with ZERO slope at both ends; a law from a start to an end radius is therefore NOT straight: measured r(0.1) 1.0589 and r(0.25) 1.1964 for 1 to 2 (a straight law gives 1.1 and 1.25). (3) The relative parameter of `UandR` is relative to the picked edge (`IinC`), not to the tangent chain: `over: "chain"` cannot be offered and `t` is per picked edge. (2) also explains the construction anomaly of VC-BLD-02 / 30.
- **Straight transitions** (superseded by 13.15: since DES-6c step 6 the kernel builds the exact polyline, and the graded nodes survive only in the OCP export) (`interpolation: "linear"`) are built by giving `Add(UandR)` the nodes of the polyline plus graded nodes (the first 1e-5 mm from an end or kink, then growing by 1.5) at its ends and kinks (`straight_law`); the contact line follows the polyline to 2e-6 mm. The face area read by the default (non-adaptive) `BRepGProp` quadrature is 170.0044 for VC-BLD-03 (an artefact of integrating a B-spline boundary: the adaptive 1e-9 reading is 170.0000005; the planar area 200 - integral of r is gated at 1e-6). The expression law of an open edge is sampled and interpolated smoothly (zero end slope); a straight expression law is `interpolation: "linear"`. Expressions use `t`, `pi`, `tau` and the built-in functions only (document parameters are not read: the step would not regenerate when one changes).
- **Profiles** (conic, curvature, asymmetric legs) are not a replacement of the OCCT blend face (the spec's `blend_profile`: the end faces and corner patches would have to be rebuilt) but a boolean of the source with the prism of the corner spandrel between the corner and the section curve (rational quadratic with weight rho / (1 - rho); quartic with zero end curvature for `shape`; the circular profile with two legs is the conic of weight sin(wedge / 2)): CUT for a convex edge, FUSE for a concave one, the two prism faces flush with the support faces. Scope: a STRAIGHT edge between two PLANAR faces, ending on flat faces square to it, ONE constant size per edge, no two selected edges at a vertex; everything else is `BLD_PROFILE_FAILED` with the reason (`blendReport`, stage `profile`). ### 13.10.2 Decisions and deviations from the sketch

- **Params are flat**, as in the pack plans: `corners: [{ name | near | all: true, type: "rolling_ball" | "setback" (default setback), setback, setbacks: [{ near | name (the edge), distance }] }]` (the sketch's nested `vertex` / `edge` objects are not used). `all` = every vertex where 3 or more rounded edges meet; a `setbacks` edge applies at every selected vertex where it meets (a single-vertex entry must name an edge that meets it). A vertex without an entry keeps the kernel's rolling-ball corner; `rolling_ball` entries are validated and recorded but leave no trace in the recipe.
- **Construction** (instead of the sketch's "OCCT fillet, trim its blend faces, drop OCCT's corner patch", which needs OCCT to build the vertex): each rounded edge is the circular spandrel prism of `blend_profile.cxx`, cut from the source between the section planes `setback` away from its vertices (a free end runs past the one flat face that closes it, so a base vertex of a pyramid works); the sharp stubs and flat end walls that leave at the vertex are removed; the support faces are split along a straight chord between the contact points on the two wall arcs (`BRepAlgoAPI_Splitter`); the hole (arcs and chords, G1 to the blend cylinders and the support planes) is filled by `BRepOffsetAPI_MakeFilling` and sewn (`BRepBuilderAPI_Sewing`, 1e-6 x diagonal) into a solid, `BRepCheck`-validated. The patch face is named `blend(v:<names of the edges meeting there>)`. OCCT's own corner is never used, so a vertex OCCT reports faulty is built the same way (no OCCT fillet is attempted at all).
- **Minimum setback.** The sketch says setback >= the edge's tangent distance. The real condition is that the setback ends beyond the point where the contact lines of the two blends on a face meet: `(t_j + t_i cos a) / sin a` along edge i (`a` = angle between the edges on that face, `t` = tangent distance `r tan(fold / 2)`), which is `t` on a right-angle corner and 0.80 mm for the pyramid apex at r 0.5. **Equal is refused** (the contact lines meet in one point and the face would pinch there); the message names the minimum: `BLD_SETBACK_TOO_SHORT`, path `corners`.
- **Scope of this build** (anything else is `BLD_CORNER_UNSUPPORTED` with the reason, or `BLD_CORNER_FAILED` for a construction failure, never a faked shape): every edge that meets a setback vertex is a straight convex edge between two planar faces, rounded in the same step with a constant circular radius (no `radiusEnd`, `sizes`, `law`, `size2`, `profile`); every rounded edge ends at a setback vertex; its other end is either another setback vertex or a vertex closed by one flat face (coplanar pieces count as one) where no other rounded edge meets; at least 3 edges per vertex. No concave edges, curved faces, or a setback vertex next to a rolling-ball vertex.
- **Fill quality and the G0 limit.** `BRepOffsetAPI_MakeFilling` hands back a B-spline approximation of the plate surface. At the OCCT defaults (approximation degree 8, 9 segments) it leaves the patch up to 6e-4 mm off the edges it is sewn to and 0.019 rad off tangent at the patch corners; the build uses plate degree 3, 15 points per curve, 2 iterations, `Tol3d` = the sewing tolerance (1e-6 x diagonal) and an approximation of degree 12 / 60 segments. What the approximation leaves does NOT follow `Tol3d` or `G0Error()` (measured: the surface is up to 40x farther from an edge than `G0Error()` says; 30 or 60 points change nothing; 200 segments roughly halve it at 6x the time; degree 14+ or 4 plate degrees are unstable): the gap to the edges is about 1.5 to 1.9e-6 x the bounding-box diagonal at every size, which is above the check_blends default of 1e-6 x diagonal. So a patch is accepted when its MEASURED gap (21 samples per boundary edge, surface at the pcurve against the edge curve) is within **5e-6 x the diagonal** (`BLD_CORNER_FAILED` otherwise), and `check_blends` judges corner contacts against 5x the default `g0` (tolerance `g0Corner`; an explicit `g0` applies to corners as given). Snapping the patch onto the exact edges (re-fitting pcurves with `BRepLib::SameParameter`, tighter `Tol2d` / `Tol3d`) was tried and changes nothing: the deviation is in the surface. The fill is deterministic; the volume depends on the point count (969.73 at 15 points, 969.52 at 30, 969.38 at 100), so the golden is pinned at 0.05.
- **Persistent vertex names** (Q7 decided as proposed: derived in core): `v(<sorted names of all the edges meeting there>)`, e.g. `v(e(box-1.1:x+|box-1.1:y+),e(box-1.1:x+|box-1.1:z+),e(box-1.1:y+|box-1.1:z+))`. The first run records `corners` in the step params with every vertex by name (by point when the name does not find exactly that vertex), expanded from `all`, the setback values kept, and for each vertex only the overrides of the edges that meet it, each as `{ name, distance }` (or `{ near, distance }` for an unnamed edge); regeneration resolves names, a gone or repeated name is `REF_LOST` / `REF_SPLIT` with the re-pick remediation. **Limit**: a parametric `fillet_edge` recorded through `executeRecorded` (`=expr` params) keeps its own `corners` as typed (the recorder only takes keys the command added, and `all` expands to a different number of entries, so no clean entry-wise merge exists): its corners are re-resolved by point / `all` on regeneration, as before names existed. Vertices coincide within 1e-7 x the bounding-box diagonal of the part in both core and native (a part at 1e5 from the origin works).
- **check_blends** now reports corner patches (`kind: "corner"`, `sourceEdges` = the edges at the vertex). The rolling-ball patches of OCCT are reported the same way; the G2 jump of a corner contact is not reported unless `require: "G2"`. G0 is measured over the whole contact, end points included; G1 on the open interior (`g1AngleRad`) and at the two end points (`g1EndAngleRad`) apart, because three faces meet at the end points: an end angle above the G1 tolerance is a `warn` `BLD_CHECK_G1_ANGLE` (the largest measured is 0.0050 rad, under the 0.01 limit).
- **No oracle case**: `tests/oracle` requires analytic sources and the patch volume has no closed form; the bounds, the spans and the golden are in `server/tests/nativeBlendCorners.test.ts`.

### 13.11.2 How a profile is built now

`fillet_profile_blend` tries, in order: (1) the **prism builder** of 13.7 for constant symmetric or asymmetric sizes on straight edges between planar faces with square flat ends (exact, unchanged); (2) the **corner builder** when selected edges meet at a vertex that is not a smooth junction of two edges; (3) the **rail builder** for everything else the prism builder cannot make and for every varying size. The prism builder's reason is dropped when the rail builder can try (no `size2`); a corner failure is never retried by the rail builder.

**Rail builder (spec 5.4, "keep the rails, change the section").** OCCT builds the circular fillet (any radius law, so a varying size has the contact lines OCCT's own variable fillet has, including its zero end slope, 13.7). For every blend face of every contour (OCCT rounds the whole tangent chain of a picked edge) the builder reads the two contact lines (iso-lines of the face, tangent to the supports), samples stations along the blend, and at each station takes A, B on the supports, the section circle through A, the mid point and B, and the apex T of the two tangent lines. The section is the conic (A, T, B) of weight rho / (1 - rho), or for `curvature` the quartic of 5.3 raised to degree 5 whose 3rd and 4th pole are moved along the support normal by `c = 1.25 kappa a^2` (a = 0.8 k |T - A|), so the section has the curvature `kappa` of each support along the section direction (read from the second fundamental form of the support face). Zero offsets are the quartic exactly: a planar support gives the closed forms of 5.3, and a sphere band measures G2 to 4e-9 / size. The surface is the tensor-product B-spline interpolating the pole curves of the stations (shared knots, periodic for a rim). Stations start at 24 and are inserted at the middle of every interval where any of the interpolated section poles misses the pole of the true section by more than 1e-8 x the diagonal (by the convex hull property that bounds the whole section) (a kink in a straight-piece law needs about 30 more; the cap is 6000). The new faces replace the old ones; the arc edge of a flat end face is replaced by the new section curve (the end face is rebuilt with `BRepTools_ReShape`); a junction with the next blend of a chain needs nothing (both sections come from the same circle). Everything is sewn (`BRepBuilderAPI_Sewing`, tolerance max(1e-6 x diagonal, twice the tolerance OCCT gave its own blend edges), at most 1e-3 x diagonal: an input of the sewing, never an acceptance rule) and checked: `BRepCheck`, one closed shell, when every blend is convex (the rolling ball inside the material), or every blend concave, the volume moves the same way as the circular fillet's and by 0.01 to 4 times as much (a profile only changes the corner cut; the window is derived in the constant's comment: the conic lies inside the triangle A T B, whose area is at most 3 times the circular spandrel's, and a conic of rho 0.95 keeps 0.016 of it at a right angle); a step that mixes convex and concave blends adds and removes material, so only its sign of material left is checked; the **measured gap** (below) is within 5e-6 x the smaller true bounding-box diagonal of the source and the result; and **two blends of a chain meet at no more than 0.0095 rad** (below; beyond the crease of the part where the chain is mitred, 13.16.4). The convexity that decides the volume check is read at the interior stations of every blend (the end stations of an open blend are skipped: a ball centre there lies in a flat end face and says nothing; a centre ON the solid is skipped), so a face whose convexity flips along its length counts as mixed; `mixed` is reported in the build notes (`data.profile.mixed`) and tested: a single convex box edge, a cylinder rim and a concave inner corner are not mixed, a boss top rim with its foot ring is.

**Corner refill.** Edges that meet at vertices are rounded by the setback pipeline of 13.10 (prisms with the profile section, stubs and walls removed, chords, `BRepOffsetAPI_MakeFilling`, sewn) with **automatic setbacks**: each edge stops 2 x the least distance that leaves the patch a face (`(t_j + t_i cos a) / sin a`, 13.10.2) from the vertex; if the fill of a patch misses the limits (a structured status, not a message search) it retries with 1.5, 2.5, 1.25 and 3 x; any other failure stops at once. The factor that built and the setback of every edge at every corner are returned with the shape (`data.profile.cornerSetbackFactor`, `.corners`), and the reason of a refusal is the one computed while building (kept by the evaluator, no second cascade), with the sizes that were tried. No `corners` entry is needed (or accepted: a profile at a setback vertex stays refused). The patch is named `blend(v:...)` and `check_blends` judges it like a setback patch.

### 13.11.3 Decisions and deviations

- **Order of builders.** The exact prism builder stays first for what it can make (its volumes are the closed forms of VC-BLD-07 to 09); the rail builder is the general one. Reason: the rail surface is an interpolation (1e-8 x diagonal), the prism is exact.
- **Varying size = the circular fillet's contact lines.** A conic or curvature profile "sized by radius" has the contact lines of the circular fillet of that radius (5.3), so a size law is read from OCCT's variable fillet (13.7: a smooth law has zero slope at both ends, a straight law is exact Law_Linear pieces (13.15)). The removed volume of a right-angle edge is then c(rho) / (1 - pi/4) times the circular one (VC-BLD-37, measured to 9e-8). `size2` (asymmetric legs) with a varying size is refused (`BLD_PROFILE_FAILED`, path `edges[i].size2`): its contact points are not the circular fillet's, so the rail builder cannot read them.
- **The whole tangent chain gets the profile.** OCCT rounds the contour of a picked edge; so does the profile. `check_blends` gives the chain members the profile of the picked edge (`blendChains.ts`, through the face graph) [superseded by 13.14.2: the chain is the kernel's]; the recipe still lists the picked edges.
- **G2 on curved supports (quintic), with a reported fallback.** The curvature offsets are clamped to a quarter of the leg. Only one failure of the curved pass is answered with the quartic: two blends of a chain whose supports' curvature jumps at their junction, so their sections differ and do not sew (a structured stage, set only for a sewing failure of a curved pass that has chain junctions). Every other failure of the curved pass (an unreadable support curvature, the station cap, a `Standard_Failure`) is refused with its own reason. A fallback is carried out of the kernel with the shape (`Shape::notes`), read back by `blendReport` (the evaluator caches the built shape, so no rebuild) and reported in the summary ("curvature profile on <edge names> fell back to the G1 quartic ...") and in `data.profile.fallback { edges, reason }`; the edges are the whole contour. G2 therefore holds except at reported fallbacks. Natural case: a sphere cut by a rounded rectangle (plane walls become cylinder walls along the rim): tested natively and through the command.
- **fillet_faces hold line + profile.** A sloped hold line is a varying size; it now builds (it was `BLD_PROFILE_FAILED` because a varying size was refused). `fillet_faces` itself is untouched.
- **check_blends.** Two named floors make the G2 reading scale-relative: a normal curvature below `1e-8 / diagonal` is flat (it was an absolute `1e-12`), and below `1e-3 / width` of the blend (width = face area / longest edge) is flat for that blend. A curvature-continuous blend that meets a plane to the noise of its rails (up to 1e-5 per mm on a 1 mm law) is G2; a conic or circular section (a curvature of order `1 / width` against a plane) is still G1.
- **Contact points are projected onto the support faces** (when closer than 1e-3 of the leg). OCCT's own blend edges are off the support by up to about 2e-6 in absolute terms, which is above 1e-6 x the diagonal on a part under 2 mm: a circular fillet of a 1 mm sphere band measures 1.28 x the default g0, the profile blend 0.67 x. With the true box only the 0.3 mm sphere band cannot meet the 5e-6 rule (gap 2.96e-6 against 2.25e-6) and is refused with the measured gap.
- **Sewing tolerance and acceptance.** The sewing tolerance is max(1e-6 x diagonal, twice the tolerance OCCT gave the edges of its own blend), at most 1e-3 x diagonal (with the plain 1e-6 x diagonal a 1 mm sphere band did not sew). It is only an input. After sewing the builder measures the real gap, the same quantity `check_blends` reads as g0: along every edge a re-skinned face shares with a neighbour, the distance between the two surfaces at the pcurves of the edge (21 samples). The edge tolerance OCCT stores is not used: it is a bound and was up to 40 times the gap. A gap above 5e-6 x the diagonal (the corner rule of 13.10.2) is refused with the measured value (`BLD_PROFILE_FAILED`: "the profile faces meet their neighbours only to X"); the builder accepts a gap only up to 0.95 of that limit (a named margin like the junction one: `check_blends` samples other points, and the entity may be placed or rotated afterwards), so the reported limit is 0.95 x 5e-6 x the diagonal; the gap and that limit are in `data.profile.gap / gapLimit`. The diagonal is the TRUE bounding box (`BRepBndLib::AddOptimal` without enlargement: the bounds `mass_properties` gives, the scale `check_blends` measures against). The acceptance limit (0.95 x 5e-6 x the diagonal) uses the smaller of the source's and the result's (a fillet that lowers an extreme shrinks the box), the construction tolerances (station criterion 1e-8, sewing input, classifier) the source's. A first version used the box of the source's VERTICES, which on a thin large disc (R 200, h 0.5) gave a limit of 2.5e-6 where check_blends allows 2.8e-3, and refused part of the small bands only as an artefact; the corner pipeline (13.10) had the same scale for its 5e-6 patch gap and now repeats that acceptance against the smaller true diagonal once the solid exists. Its 1e-7 vertex-matching tolerance deliberately stays on the vertex box (core matches vertices with the same scale, `geometry/blend/vertices.ts`) and decides no acceptance.
- **Junctions are measured.** `check_blends` adds a `junctions` list to a blend row: the edge where it meets the next blend face of its chain (a blend that is not its support), G0 against `g0`, G1 against `g1AngleRad`, measured once from the lower face. Chain members get the profile through the face graph across edges whose measured angle is under 0.05 rad [superseded by 13.14.2: the chain is the kernel's] (`edgeConvexity` is not used: it labels a tangent junction of two profile blends "concave"), so a `fillet_faces` blend that meets a profiled face at a crease keeps no profile. Face names with the `#k` suffix of a pair of faces that meets twice (`blend(e(A|B)#2)`, a sphere cap cut by walls) were not recognised by `check_blends` at all; they are now, and their contacts and junctions are measured.
- **Chain junctions are held to the check_blends default, or refused.** The apex of a section moves with the fold angle, whose derivative jumps where the curvature of a wall jumps, so two blends of a chain kink there: 8.8e-6 rad on a rounded outline over planar caps, but up to 0.018 rad on a sphere cap cut by a rounded rectangle. The builder measures the angle between the outward normals of two re-skinned blends along every edge they share (at the gap samples) and refuses above 0.0095 rad, 0.95 x the `check_blends` G1 default (0.01; the margin keeps `check_blends`, which samples the junction at other points, from ever reading above the default), with `BLD_PROFILE_FAILED` naming the angle and the limit. A curvature profile whose curvature-continuous pass kinks or does not sew is rebuilt as the quartic (the reported fallback); if the quartic kinks too the refusal names both passes. The largest junction angle of a build is reported even when it passes (`data.profile.junctionG1`, and in the summary when above zero). So `fillet_edge` does not return a shape its own `check_blends` default fails at a junction (the R 20 cap with blend 0.5: curved pass does not sew, quartic 0.0087 rad, built with the reported fallback; blend 1: curvature refused, the conic 0.0077 rad builds; R 30, corner 2, blend 1: conic 0.0182 rad refused). The refusal limit is 0.0095 rad.. Specifying the end velocity of the interpolation was tried and changes nothing: the kink is in the sections.
- **One G0 rule for profile faces.** Re-skinned profile faces are B-spline approximations like corner patches, so `check_blends` judges their contacts and junctions against a named `g0Profile` = 5 x g0 (listed in `tolerances` when the check holds a profile row; an explicit `g0` applies as given), and the builder refuses at exactly that limit (5e-6 x the diagonal of the source vertices, never more than `check_blends` computes from the bounding box). Circular and prism-built rows keep g0. The gap is sampled at four times the knots of the blend surfaces along each edge (at least 21 points).
- **Junctions only within one profiled step.** `check_blends` takes an edge between two blend faces for a junction only when both belong to the same fillet node (recorded in the law record) and that node has a conic or curvature profile: blends of two steps, a mitre of two blends of one circular step, or a crease against OCCT's own corner face are creases by intent and are not measured (a first version measured them and warned "contact line(s) could not be measured" on plain circular blends). Junctions the kernel cannot measure are counted apart (`unverifiedJunctions`, own message), never as contacts. A profile reaches the other blends of its chain across edges where the measured angle is under 0.02 rad (twice the G1 default). [superseded by 13.14.2: the chain is the kernel's]
- **Profiled edges that meet at a vertex with a varying size** are refused before any builder runs: "profiled edges that meet at a vertex need one constant size" (the corner builder assumes one size per edge). Before, the rail builder answered "ends obliquely" or "not an iso-line".

### 13.11.5 Left (exactly) and what OCCT cannot do

Not built, each refused by name with `BLD_PROFILE_FAILED` and the reason:

- **Corners of curved edges or non-planar faces** (profiled edges meeting at a vertex where an edge is curved or a face is curved), **vertices with an unrounded edge** (two rounded edges and a third left sharp: the blends would have to be intersected and trimmed), **a profile with a `setback` corner** (`corners` still refuses a profile: M3 remainder). The corner patch is G1 only (13.10.2), also with a curvature profile.
- **Ends**: a blend that ends obliquely on a face, on a curved face, or on a corner patch of OCCT's own (the end edge is then not a section; refused as "ends obliquely"). A blend that ends square on a flat face, on the next blend of a chain, or closes on itself is built.
- **Asymmetric legs (`size2`) on a curved edge, on curved faces, or with a varying size.** The contact points of a leg pair are not the circular fillet's, so OCCT cannot supply the rails (a different rolling-ball construction would be needed).
- **Solids with a void**: built since §13.17 (a second body outside the first is still refused by name).
- **Parts of about 0.3 mm**: OCCT's own circular fillet is already 5 to 17 x off 1e-6 x diagonal below 3 mm (an absolute approximation error of about 1.6e-6 to 3e-6); the profile blend builds from 0.4 mm (sphere band; rims from 0.3 mm) and the 0.3 mm band is refused with the measured gap (13.11.3).
- A straight-piece (kinked) law gets about 30 extra stations around each kink; a very sharp one can exceed the cap and is refused with the measured deviation.
- **Profiled edges that meet at a vertex with a varying size** (see 13.11.3): refused.
- **A chain whose blends would meet at more than 0.0095 rad** (see 13.11.3; beyond its crease where the chain is mitred, 13.16.4): refused, with the angle; a smaller blend or the conic usually builds.
- **Parts of about 0.3 mm** when the circular blend of OCCT is not accurate enough: refused with the measured gap (13.11.3). The blend-to-blend junctions of a chain kink where the curvature of a wall jumps (up to 0.018 rad measured); above 0.0095 rad the build is refused, not repaired.
- **No test can provoke the volume sanity check** (sign and 0.01 to 4 times the circular fillet's change, when all blends are convex or all concave): it guards an inside-out rebuild that none of the geometries tried produces; the mixed rim + boss-ring case is tested to build.
- The rest of DES-6c is as in 13.9 and 13.10.4 without M2: M3 remainder, M4 remainder, M5, `llull guide` Blends, VC-26, `over: "chain"`, true straight laws.

### 13.12.2 Decisions

- **Concave corners are the convex construction with the other boolean.** A concave edge's spandrel prism is fused instead of cut (`Tool::convex = frame.convex`); stubs, walls, chords, the hole and the fill are identical (the hole is bounded by the same arcs and chords). Differences: a concave blend that ends on a closing face must end flush (square to it; an oblique end is `BLD_CORNER_UNSUPPORTED`, because running past the face would add material outside the part); the end cap of a fused prism stays a face next to the closing face, so the fused solid goes through `ShapeUpgrade_UnifySameDomain` (faces only) and the tool faces carry no name, so a merged face keeps the closing face's name (`z+`, not `tool.4`); the volume check is "smaller" for convex corners, "larger" for concave ones, "a solid" for a step with both.
- **Profile corners stay convex only.** The automatic (profile) corner mode shares the builder; removing the convexity refusal also let it build on concave edges, which nothing covers, so `edge N is concave: profile corners round convex edges` is restored for it (Rust test `profile_corners_on_concave_edges_are_refused_by_name`). Profile corners on concave edges are a separate item (13.12.5).
- **The face merge after a fuse is limited to the tool's own faces.** `UnifySameDomain` ran on the whole solid and would merge a face split by `split_face` or an imported coplanar face, losing a name (REF_LOST on replay). The faces that come from the tools carry no name (the originals always do: `f<k>` at least); every edge that does not bound such a face is passed to `KeepShapes`, so only cap faces merge. `server/tests/nativeBlendCorners.test.ts`: split a cube face, then a concave setback: both halves keep their names and the history replays.
- **The least setback is a fixed point.** With a radius linear along the edge the tangent distance at the setback is `a + g d`, and every distance the neighbours' blends reach is linear in `d`, so the least setback per term is `c0 / (1 - c1)` (closed form); a slope `c1 >= 1` (the radius grows as fast as the setback) is `BLD_CORNER_UNSUPPORTED` ("no setback outruns it"). The minimum in `BLD_SETBACK_TOO_SHORT` is the JOINT one (review round 2: holding a neighbour at its given setback is a true minimum only at right angles): when every edge was given the same setback it is the least uniform `d*` = max of the self terms `a_i / (1 - g_i)` and the cross terms `(a_j + a_i cos) / (sin - g_j - g_i cos)` over the faces at the vertex, with a denominator <= 0 refused by name (`BLD_CORNER_UNSUPPORTED`, "no setback outruns the blends"); when the setbacks differ it is the least fixed point of the setbacks of all the edges (iterated from 0), and the message lists every edge's minimum. The number after "must exceed" x (1 + 1e-6) builds and x (1 - 1e-6) is refused (Rust tests: equal edges at 90 degrees, a pyramid apex with a taper, unequal edges at 90 degrees, a setback per edge).
- **The built gap is measured at 101 points, with a ladder of fits.** `check_blends` accepts up to 101 samples per contact; the builder measured 21 and missed peaks near the hole corners (a pocket corner: 6.4e-6 x the diagonal, over the 5e-6 limit). It now measures 101 (cost: negligible). A patch over the limit is filled again with the next of five fits (points per curve, approximation degree, segments; the order is below); the gap is not monotonic in the settings, so the ladder is a search, not a refinement. A corner that needs the later fits costs 130 to 800 ms instead of 175 ms; the cube needs none. Bound: at most 5 fills per patch of a setback corner, and at most 25 per patch of an automatic profile corner (5 setback factors x 5 fits). The order is by the success rate measured on the 38 Rust blend tests (255 patches; the first fit succeeded for 77%; of the 58 that failed it, the second solved 60%, the 40-point fit 73% of the 15 left after the 13/100 and 25-point fits had failed, the 13-degree fit 29% of 21, the 25-point fit 9% of 23), so the ladder is 15/12/60, 15/14/100, 40/12/100, 15/13/100, 25/12/60. Trying only the first fit on every factor but the last was measured and rejected: it changes which setback factor wins (1.25 instead of 1.5 on 4 patches of the rail tests), so every factor still tries the whole ladder (110 s against 159 s for those tests).
- **Each patch is classified against the source.** The centre of mass of a patch must lie IN the source solid for a convex corner and OUT of it for a concave one (`BRepClass3d_SolidClassifier`), per corner, so a step that mixes both kinds is checked too (the volume sign check alone was vacuous there). The tolerance is max(1e-7, 1e-9 x the diagonal). A patch on the wrong side is not `fill_failed` on purpose: it is a logic failure of the construction, a finer fit would not change it, so the profile corner does not retry another factor.
- **A vertex is all convex or all concave.** A vertex where both kinds are rounded (the rim of a notch: one concave edge and two convex ones) is `BLD_CORNER_UNSUPPORTED` ("convex and concave edges meet at ..."): the hole would be bounded by blends that remove and blends that add material, and the patch would have to change sides.
- **A linear radius is a cone.** For r(s) linear between the start and end of the edge the section circles at two stations are homothetic about a point of the edge line, so the ruled loft (`BRepOffsetAPI_ThruSections`, ruled) of the two circular spandrels is exact: its arc face is a cone tangent to both supports along the ruling lines. The tool runs between the setback sections (the radius there is the law's value at the setback, extrapolated past a free end), the minimum setback is checked with the tangent distances AT the setback sections `(t_j + t_i cos a) / sin a`, and the rest of the pipeline is unchanged. The **smooth** `sizeEnd` / `radiusEnd` (the kernel's S-curve with zero end slope) and multi-station laws are refused: their sections are not homothetic, the tool would need a loft through many stations. `check_blends` does not compare the realised radius with a law that varies along an edge whose blend stops at setbacks (it assumed the blend face spans the whole edge: it read the radius 0.8 + 0.4 x 0.25 at t = 0 and failed); the radius readback is still reported. Review round 1 changed this: skipping the comparison hid a wrong radius (a reversed taper), so `check_blends` now projects the first and last section mid points onto the (straight) edge line and compares the law over the span the blend covers, `radiusAt(law, lo + t (hi - lo))` (or reversed), for constant and linear laws (`checkBlendRadius.ts` `setbackSpan`; unit cases in `tests/unit/blendReadback.test.ts`; the native test reads 0.09 and 0.11 x size at the two blend ends of an edge whose law is 0.08 to 0.12 x size and setback size / 4).
- **Speed.** The corner acceptance measured the diagonal of the finished solid with `AddOptimal` over B-spline patches of 90 x 90 poles at degree 12: 540 ms for 8 corners (68 ms per corner). It now takes the box of the other faces plus the edges of the patches, a lower bound of the true box, so the limit is never looser than check_blends' (`lower_diagonal`; the refusal message says "the lower bound of the result's box"). The fill (175 ms per corner) is unchanged: a 30-segment approximation halves it (85 ms) but leaves the patch 3.2 to 3.4e-6 x the diagonal off its edges and put the end-point angle of the profile cube at 0.0121 rad on a 1000 mm part (`blend_rail_tests`, above the 0.01 default), so it was tried and removed. The corner takes about 205 ms on the native build (275 ms before; from the lap timings of the build), so the 200 ms budget is nearly met there (the later fits of the ladder cost more on a corner that needs them), not in the whole step (tessellation of the patches adds about 0.5 s per 8 corners). The in-loop gap limit is now the accepted one (0.95 x 5e-6 x the diagonal), so a patch the post-solid check would refuse is refused at once.
- **G2 patches are not possible with `BRepFill_Filling`.** `Add(edge, face, GeomAbs_G2)` and `GeomAbs_C2` both raise "The continuity is not G0 G1 or G2" for these faces, so no `continuity` parameter was added.
- **Decided, not built:** setback corners with a rolling-ball neighbour (the builder makes no OCCT fillet at all; mixing needs a second fillet on a solid whose blend ends are new faces), on curved or non-straight edges (the tools are straight prisms / lofts), and with a profile (the profile corner builder keeps its automatic setbacks).

### 13.13.2 Decisions

- **Meeting faces go through the edge path.** A rolling-ball blend of faces that share an edge IS the blend of that edge; building it with fillet_edge's builder gives curved faces, profiles, laws, chord mode, the continuity checks and `check_blends` for free, and no second law vocabulary (`law`, `radiusEnd`, `width` are `edges[].law`, `radiusEnd`, `mode: "chord"` of fillet_edge). Reason: the spandrel build (13.7) is exact only for planar faces and flush square ends; a curved-face spandrel in C++ would duplicate the profile builder for no gain where the faces meet.
- **Every pair that shares a sharp edge goes through the edge path**, a plain constant radius of one planar face against one planar face included (review round 1: the same pair was refused with `radius` and built with `radiusEnd` or `width`; the inconsistency is gone). The spandrel `faceBlend` build is used only when the sets share NO sharp edge: one planar face per set with a constant radius (the faces between them are consumed). No compatibility with the old routing is kept (owner rule): `fillet_faces` of an adjacent pair now records a `fillet` node, not a `faceBlend` node.
- **The kernel's chain is the truth, and the blend never leaves the sets.** OCCT rounds the whole tangent chain of every picked edge (13.7) and its chaining reaches about 0.1 rad: measured on extruded regular N-gon prisms (R 50, depth 20, top against ONE side face, r 1), N = 120 / 100 / 64 (turn 0.052 / 0.063 / 0.098 rad) chain every side edge and N = 56 or fewer do not. A geometric closure (an earlier round used 0.05 rad) is therefore a second, wrong rule and was removed. `readEdgeResult` (`faceBlendEdges.ts`) builds with the shared edges, then reads the built result: every NEW blend face (`blendSource` of its name: source edge name and the two support face names) must rest on faces of `facesA` U `facesB`; otherwise the blend is refused (`BLD_FACE_BLEND_UNSUPPORTED`, path `facesA`, the edges and the out-of-set faces named) and the document is unchanged. `data.blendEdges` lists the kernel's chain (the source edges of the new blend faces, by name). The hold line goes through the same read-back.
- **A varying size needs a kernel chain of exactly one edge.** `t` runs along each picked edge (13.7: `over: "chain"` is not built), so a law over a chain would restart at each junction. The sets must share one edge (checked before the build) and the read-back must show one new blend face; otherwise `BLD_FACE_BLEND_UNSUPPORTED`, path `radiusEnd` / `widthEnd` / `law` / `holdLine`.
- **`startNear`** (a point near the end where t = 0): the end nearer to it starts the size; the other direction is the reversed law (`reverseLaw` in `geometry/blend/law.ts`: the sampled law with its sizes swapped and its control points mirrored, i.e. evaluated at 1 - t, not an edit of the expression text). Without it the edge's own direction applies. On a closed edge (a rim: no start end) it is refused at path `startNear`, naming the seam vertex. `data.blendEdges` is `[{ index, start, end }]` with `start` the point where the first size applies (the summary prints the same, in that order).
- **Refusal paths are `fillet_faces` params:** `law.expression`, `radius` / `width`, `radiusEnd` / `widthEnd` (`law` for a non-periodic law on a closed edge), in `error.paths` and in the summary suffix.
- **`width` is the chord** between the two contact lines (fillet_edge `mode: "chord"`; right angle: r = width / sqrt 2). `widthEnd` is the chord at the end.
- **Tangent (`smooth`) shared edges are not blend edges**; a face of a set that touches the other set nowhere is only a support (the summary and `data.blendEdges` list the blended edges).
- **Tolerances and the check default:** nothing new to tune: the sizes, the `kGapAccepted` margin and the profile gates are the ones of fillet_edge (13.11.3); a law was run at the lowest and highest `samples` (5, 257) and passes `check_blends`.
- **`data`** on the edge path is `{ id, blends, consumedFaces, unit, blendEdges }`; `blends` is read from the result topology by the helper `faceBlendData` shared with the spandrel path.

### 13.14.3 M5 as built

- **Variable chamfer** (`chamfer_edge` `distanceEnd`; recipe `chamfer` + `sizeEnd`). OCCT has no chamfer law (`MakeChamfer` takes distances), so the section construction of §5.7 is used: for each listed straight edge between two planar faces, ending on flat faces square to it, the ruled loft (`BRepOffsetAPI_ThruSections`, ruled) of the two corner triangles (corner, point at the distance on face 1, point at the distance on face 2) with the distance `distance` at the edge start and `distanceEnd` at its end; CUT for a convex edge, FUSE for a concave one (`apply_tools`, the spandrel tool pipeline). The lateral face is a bilinear patch whose cross-section at every station is the straight chamfer section of that station's distance, so a right-angle edge of length L loses exactly 1/2 integral d(s)^2 ds = L (d0^2 + d0 d1 + d1^2) / 6, and a concave one gains it. The face is named `chamfer(<edge name>)` (the role OCCT's own chamfer faces use), so persistent names, `edit_step_params` and replay work as for `chamfer_edge`. Symmetric legs only (`distance2` / `angleDeg` with `distanceEnd`, `distanceEnd` <= 0 is `BLD_CHAMFER_VARIABLE_PARAMS`, path `distanceEnd`), edges listed (no "every edge": `BLD_CHAMFER_VARIABLE_PARAMS`, path `edgeIndices`); the remediation is "distanceEnd: > 0, symmetric legs (no distance2 / angleDeg), list the edges". What the builder cannot make is refused with the reason it computed (`BLD_CHAMFER_FAILED`, path `distanceEnd`, stage `chamfer` of the blend report; remediation: smaller distances, unlist edges that share a vertex, or a constant chamfer): a distance that reaches past the faces (checked at 5 stations), edges that share a vertex ("need a constant distance"), a curved edge or face, an end not on a square flat face, a listed edge twice, an out-of-range index. The step is recorded by edge name; the manifold kernel refuses it; `export_code` carries the exact result (`BLD_CODEGEN_UNSUPPORTED`), never a constant chamfer. `check_blends` has nothing to measure: a chamfer is not tangent by design.
- **Per-joint `blend_union` radii** (`joints: [{ near, radius }]`; recipe `blend` + `joints`). A pick selects the joint (a section edge of the fuse) nearest to the point (the semantics of `edgesNear`) and rounds it, with the joints tangent to it (OCCT rounds a whole contour), with the pick's radius; every other joint takes `radius`. Two picks that fall on one tangent chain are fine with the same radius and refused with different ones (`MakeFillet::Contour` tells which contour an edge is in), with the reason in the summary (the blend report of stage `blend`). Solids that share no joint, given `joints`, are refused too (`BLD_JOINT_PARAMS`, path `joints`). A pick whose distance to its nearest joint exceeds 10 x that pick's radius is refused with the distance and the bound in the reason; every pick refusal is `BLD_JOINT_PARAMS` with path `joints[i].near` / `joints[i].radius` (radius <= 0, two radii on one chain, a pick too far; remediation: one radius per tangent chain, every radius > 0, every point within 10 x its radius of a joint). The kernel reports each pick's distance to its joint (`notes.picks`) and `data.joints` of the command lists `{ index, distanceToJoint, radius }`. Without picks the build is the old one edge for edge. In-process kernels (which cannot honour per-joint radii) refuse a recipe with `joints` instead of rounding every joint alike. `check_blends` takes a `blend_union` result for a blended solid (`hasFillet`) and **verifies** the radius of each joint: the kernel's notes list, per contour of joints, the radius it got and the names of its joint edges; `lawIndex` turns them into a constant radius law per joint edge (`LawRecord` without a source edge: a constant law needs none), so a realised radius off its target by more than 1e-4 relative is `BLD_CHECK_RADIUS_LAW` (fail) like a fillet law; each joint row (and `LawRecord`) carries its `source`, the pick that named it (`joints[i]`) or `default`, so a mis-pick shows in the check output (the kernel notes carry it per contour); a kernel that reports no contours verifies nothing and still reads the radius back (VC-BLD-32): the rows of kind edge read 0.5 and 1.5 x size to 1e-6 x size. The description of `check_blends` covers `fillet_edge`, `fillet_faces`, `fillet_full_round` and `blend_union`.
- **One build per `blend_union`.** The blend report of a `blend` node reads the notes of the cached built shape (no second build, so `check_blends` adds none); the reason is computed, with a rebuild, only when the node does not build. Measured on the native build, one `blend_union` with joints through the server including tessellation: 21 / 20 / 21 / 22 ms at 1 / 10 / 100 / 1000 mm before, 13 / 11 / 12 / 15 ms after.
- **Codes added to §7.1:** `BLD_CHAMFER_VARIABLE_PARAMS` (raised by `chamfer_edge` before the kernel runs), `BLD_CHAMFER_FAILED` (the kernel cannot build the variable chamfer; the reason it computed is in the message), `BLD_JOINT_PARAMS` (`blend_union` `joints`). Their remediations are in `blendCodes.ts` and `diagnose.ts`.
- **Guide.** `llull guide` is one document; the Blends topic is its section 14: when to use `fillet_edge`, `fillet_faces`, `fillet_full_round`, `chamfer_edge`, `blend_union`, `probe_fillet`, `check_blends` (the profile blend is the `profile` param of `fillet_edge` and `fillet_faces`; `fillet_profile_blend` is the native operation, not a command), laws, profiles, setback corners, the main refusals with their remediation, and a worked plan (probe, varying radius, variable chamfer, conic round, check each; it runs natively as part of `target_m5`). `tests/unit/conventions.test.ts` checks that the section exists, that every command it names is registered, that every BLD code it lists exists in the blend sources, that the worked plan's params pass their command schemas, and that it states what is not offered.

### 13.16.2 What OCCT gives (measured, native llull-kernel, OCCT 7.9.2)

On the top rim of a 64-gon prism (R 50, depth 20, r 1) OCCT rounds the whole rim as a chain of 64 blends. Each blend face is a **cylinder** (uv [0, pi/2] x [0, 4.907]); its two end edges are the iso-lines v = 0 and v = 4.907, i.e. circle arcs **in the plane perpendicular to the blend's own axis**. The neighbour's arc is the same edge topologically but not geometrically: the two arcs miss at the contact point on the top plane by exactly r x turn (0.098), and the shared edge carries the tolerance 0.103 that hides it. The rail builder took the section circle at the end iso-line and so built every face ending on its own section plane. Consequences found on the way: the volume of OCCT's own circular solid there is not integrable (`mass_properties` change -290.04 where the removed volume is about +67; the old volume window used it), and `BRepClass3d_SolidClassifier` rebuilt per ball centre cost 2.7 s for 64 x 24 stations.

Where OCCT chains (the limit is its tangency tolerance, not ours): regular polygons of 64 sides (turn 0.0982 rad) and 120 sides chain, 60 sides (0.1047) do not; a bent bar chains at 0.09 and 0.099 rad and does not at 0.1 or 0.1005. Not chained, the blend runs out onto the next wall and the existing "ends obliquely" refusal applies.

### 13.16.3 The construction

**Mitre plane.** For two blends that meet at an end, take each blend's end section (the circle through the contact points and the arc midpoint, as before) and its plane: unit normal `d` pointing out of the blend, through the ball centre `c`. The mitre plane is the bisector plane of the two section planes, the plane of equal signed distance beyond each: `(d1 - d2) . x = d1 . c1 - d2 . c2`. For a prism rim it is the symmetry plane of the corner (it contains the vertical edge of the part and the bisector of the polygon). Both blends compute the same plane from the same pair (`plan_mitres` reads every end section before any mitre moves one).

**Displacement.** Every point of the end section (contact points A, B, apex T, ball centre) slides along `d` onto that plane: `shift = d (q - n . P) / (n . d)`. The conic (A, T, B) of one blend is then the affine image of its section, and the end section of the neighbour is the same curve (by the symmetry of the corner), so the two faces share their end section exactly. For a prism rim the faces stay **exactly on the swept profile**: the rows of the surface (the A, T, B pole curves) are straight rulings, the displacement only reparametrises them, and a conic surface through rulings lies on the extruded conic whatever the parameters.

**Fade.** The displacement is faded in over the half of the blend nearest the end by the quintic smoother step (zero first and second derivative at both ends), so the interpolated pole curves stay smooth and the station refinement (1e-8 x diagonal) converges: a mitred 64-gon blend ends with 41 stations. The transition must be 4 times longer than the largest displacement (the speed of a row is 1 + shift x fade', fade' at most 1.875); a shorter blend is refused with the rule and the values ("half of it (L) must be at least 4 x the displacement of its end section (D, so 4D)"). A size that is not constant (a range law such as 1 -> 1, `radiusEnd`, `sizes`, `law`) is refused by `plan_mitres` itself ("needs a single radius (no radiusEnd / sizes / law, even 1 -> 1)"), whatever OCCT does: the mitre is exact for straight edges with a constant size.

**Support faces.** The rails of a mitred blend end at the new points, so the planar support that bounds them is re-trimmed: its rail edges are replaced by the rail curves of the new surface (`UIso`) between a vertex shared by the two neighbouring rails (the top face of the rim loses its 0.098 wedges), with new pcurves on the plane (`rebuild_face`, which also does what the end faces needed). A contact point that sits on an edge of the part (the wall rail ends on the vertical edge between two walls) is pinned: it may move by at most 1e-6 x the diagonal, else the build is refused (13.16.6). The sewing tolerance no longer counts the tolerance OCCT gave the edges where two blends meet (0.103 here, all remade); it is the tolerance of the other blend edges, so a 64-gon sews at 1e-6 x the diagonal instead of the 1e-3 cap.

**Checks that changed.** (1) The volume window compares with the circular volume read from OCCT's solid; at a crease it is integrated from the mitred circular sections instead (area between the corner and the arc, along the ball-centre path). That is a sanity window (it catches an inside-out rebuild), not an independent oracle: it is integrated over the same mitred sections. The oracle is the swept-section volume of the tests. (2) The result box that sets the acceptance limit samples the blend faces (17 x 8 x knots points) and searches the other faces exactly: `BRepBndLib::AddOptimal` took 1.0 s (conic) to 3.0 s (curvature) on 64 blend faces, a build now takes 0.7 s and 1.4 s there; the box differs by far less than the 1e-6 relative the limit needs, and the 24 existing rail tests are unchanged. (3) The ball-centre classification reuses one classifier (2.7 s -> 0.3 s). (4) A mitred result is read with the adaptive mass rule (`refined_mass`): the fixed Gauss rule is off by 1.4e-4 of the removed volume (5e-8 of the total), the adaptive one by 1.4e-7 (conic) / 3.0e-7 (curvature).

### 13.16.4 Decision: the junction kink of a creased chain

The two blends of a junction are tangent to **different** support faces at its two ends: at the top-plane end both are tangent to the top plane (angle 0), at the wall end blend i is tangent to wall i and blend j to wall j, so their normals differ by the **crease of the part** itself (0.098175 rad = 2 pi / 64 to 1e-12, measured on the 64-gon, 0.0990 on the bent bar). No profile can be G1 across a junction there; the circular fillet has the same angle. The junction angle is not the defect to bound. The interior of the junction never exceeds its end value (for the circular blend the angle between the normals at the angle phi of the section is acos(sin^2 phi + cos^2 phi cos(turn)), at most the turn; measured: the largest junction angle equals the crease for both profiles).

Decision, with that reason. The allowance for the crease is **never measured on the blends under test** (that would let any end mismatch widen its own limit). In the builder it is the `turn` that `plan_mitres` computed from OCCT's circular sections, stored in the `Mitre`, and only for the junctions whose two blends were mitred; every other junction, in a step that mixes a mitred chain and tangent arcs, keeps the plain 0.0095 rad (0.95 x the check_blends default). In `check_blends` it is the **crease of the support faces**: for a junction of blends i and j, the angle between the normals of a support of i and a different support of j along the sharp edge those faces share (the edge between two walls of a rim; `supportCrease`, one `edgeContinuity` query per pair; of several edges two supports share, the one with an end on the junction edge; a pair above the cap is skipped before the maximum is taken). It is 0 for a smooth chain (the same supports, or tangent ones), 0 below 1e-4 rad (noise) and **0 above `CHAIN_CREASE_LIMIT` = 0.11 rad** (OCCT chains up to about 0.1; a larger crease is a corner of the part and gets no allowance). A junction is then judged by `judgeJunction`: the interior and every sample by `g1AngleRad` + the support crease (BLD_CHECK_G1_ANGLE), and each of the two ends by its distance from what the supports there give, 0 (both blends touch the same support) or the crease (each touches its own), which must be within `g1AngleRad` (a second BLD_CHECK_G1_ANGLE, "differs from the crease of the supports"). A smooth chain, whose crease is 0, gets the plain `g1AngleRad` rule exactly. `data.profile.creaseRad` (the largest planned turn) and `junctionG1` report both on the build; the junction row of `check_blends` carries `creaseRad`. Unit tests (`blendChains.test.ts` for the pure functions, `blendJunctionVerdict.test.ts` through `check_blends` over a scripted kernel with fake face queries, where a smooth chain with ends 0.005 and an interior 0.012 fails BLD_CHECK_G1_ANGLE): a smooth chain with ends 0.005 and an interior 0.012 fails; across a crease of 0.098 an interior of 0.12 fails, ends of 0.0982 and 0 pass, an end at 0.05 fails; a support crease above the cap gives no allowance. The G1 of the contacts with the supports is unchanged (1e-6 rad class; the Rust tests assert the support contacts below 1e-5 rad and the junctions below turn + 0.0095 apart).

## 13.19 As built: a conic that fades to the circular arc at a kinked chain junction (DES-6c, 2026-10-30)

### 13.19.1 Why the junction kinked, and what cannot fix it

A blend of a chain meets the next one along a section: both end sections are the circular fillet's, so G0 holds. The normal across the junction does not: the profile section is the conic a, t, b with the apex t (the intersection of the two tangent lines), and the surface normal in the interior of the section depends on the derivative of t along the rail. t moves with the fold angle of the walls, whose derivative jumps where the curvature of a wall jumps (a plane against a cylinder on a rounded outline), so the two blends have different along-rail derivatives at the junction (13.11.3: 0.0182 rad measured on an R 30 sphere cap cut by a 2 mm rounded outline; limit 0.0095 rad).

Why no change of the conic repairs it: G1 against the walls requires t to lie in both wall tangent planes at the contacts, a line along the rail, so only the out-of-plane part of t' is free; the in-plane jump of t' is not. A weight w(s) alone cannot cancel a vector jump that changes with the section parameter. The circular section has no such dependence (its normal is radial, whatever the frame does): the rolling ball is G1 across any wall-curvature jump.

### 13.19.2 The construction

When the first pass is refused for a junction kink (conic only), `rails_blend` runs a second pass in which every blend end that meets the next blend of its chain (and is not mitred: a mitre keeps its crease allowance) fades to the circular arc. The weight of the rational quadratic goes from the profile's (rho / (1 - rho)) to the circle's (cos of half the arc, the weight that makes a, t, b exactly the ball's arc) by a quintic smooth step of the arc length of the ball centre: share 0 at the junction (the section IS the circular arc there, so the surface is the rolling ball's and G1 across the junction), 1 at the fade length, with zero first and second derivatives at both. Length = 3 chords |a b| of the end section (`kFadeReach`), at most 0.45 of the blend. The weight varies per station, so the middle pole row is interpolated as w x P beside the weight curve (same parameters, same knots) and the surface is the ordinary NURBS with those weights; the along-rail refinement criterion of 13.11.2 compares w x P and the weight. Closed blends (rims) have no ends and no fade. A first pass that builds is untouched (byte-identical results). A curvature profile has no fade (its section is a polynomial of degree 5, no circle in it): its refusal is unchanged and names both passes.

`data.profile.circularFade` = `{ ends, reach, reachChords }` and the summary sentence say that it happened; the profile there differs from the asked one by the weight change (here 0.81 to 1.0 of the circle's against the conic's weight 1, within 3.86 mm of each junction).

**Why the fade is G1 across the junction (the carrying argument).** The junction section of a faded end is OCCT's circular iso-arc: a, b are its contacts and t the apex of its tangent lines, and the weight there is the weight of its own section circle (cos of half the arc, read from the section, so a varying size is covered: the circle changes along the chain, the weight follows it). The weight curve is built so that its derivative along the rail equals that of the circle's weight wc(s) at the junction (the quintic share has zero first and second derivative there, so w'(s) = wc'(s)). The rational surface a B0 + w t B1 + b B2 over B0 + w B1 + B2 with w = wc(s), a(s), b(s), t(s) the circle's own data is the circular blend itself, and OCCT's circular chain is G1 across the junction (the rolling ball): the faded blend is tangent to it to first order at the junction from both sides, hence G1 with its neighbour. Two approximations carry the claim to a measured 2.3e-6 rad, not to zero: the contact points are snapped onto the support faces when closer than 1e-3 of the apex distance (OCCT's own contact error, section 13.11.3) and the end slope of the interpolated weight curve is the spline's, not wc'(s) exactly.
