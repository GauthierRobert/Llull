# BLD — Validation pack

Proves a future implementation of [FUNCTIONAL_SPEC.md](../FUNCTIONAL_SPEC.md) / [TECHNICAL_SPEC.md](../TECHNICAL_SPEC.md).
"Validated" = every grade-A `VC-BLD-*` passes on the **native OCCT kernel** in an automated gate (oracle + golden + server), and the

## 4. Findings from the reference scripts and the code reading

1. **Planar face areas are construction-independent; volumes of variable fillets are not.** A sphere of radius r centred r from a
   plane touches it at the foot point, which also satisfies the envelope's characteristic condition, so the contact lines of a
   variable fillet are the same for the section construction and the rolling-ball envelope. The removed volume differs: −0.08 %
   at mid-span for slope 0.05, −0.33 % in total for slope 0.1 (`data/extra_cases.json`). Variable-law VCs therefore gate on face
   areas (1e-6) and use a construction band for volume; VC-BLD-30 pins the construction OCCT uses.
2. **Conic sizing has an exact anchor.** The segment ratio `f(w)` is affine-invariant, so one closed form (ellipse / parabola /
   hyperbola branch) covers every wedge angle; rho = √2 − 1 on a 90° edge reproduces the circular volume to 1e-12, and the
   asymmetric circular case is the elliptic quarter `(1 − π/4) d1 d2`.
3. **A circular fillet is never G2 to planes** (curvature jump 1/r); the quartic section `A, A + k(T − A), T, B + k(T − B), B` has
   zero end curvature for every k and removes exactly `0.1 d²` at k = 0.5 on a 90° edge — a clean G2 oracle.
4. **Face-face fillet across a chamfer has a sharp feasibility bound** `r ≥ c/(2 − √2) = 1.70711 c`, which gives both a value VC
   (r 2) and a refusal VC (r 1.5).
5. **Measured on the native kernel (DES-6, M0): OCCT's linear radius law is a third construction.** For r 1 -> 2 and 1 -> 3 on the 20x10x5 block the planar face areas are exact (170 / 70, 160 / 60), but the volume is 989.896821 and 981.047466: 8.9e-5 and 3.6e-4 relative BELOW the normal-section value, and 0.415 mm3 below the envelope value in the 1 -> 3 case. A 1e-4 deflection mesh agrees with the Gauss-rule volume, so this is the construction, not the integration. Volume gates for variable laws therefore use a measured band (oracle 110: 2e-4, oracle 111: 5e-4) and the planar areas carry the 1e-6 check (VC-BLD-02, VC-BLD-30; `expected_results.json` `measuredNative`).
6. **Code facts that change the scope**: `fillet_edge` already reads start/end and control-point laws per edge (SC-F3) and chord
   sizing on planar faces; the native kernel builds them — but no oracle case covers them, OCCT's failure status is discarded,
   native `edgeContinuity` / `edgeSamples` answer null, and codegen drops variable fillets. M0 is about these.

7. **Measured on the native kernel (DES-6b)**: OCCT's `Add(r1, r2, E)` law is not straight (a cubic with zero end slopes; `ChFiDS_FilSpine` source read, and `Add(Law_Function)` crashes in 7.9.2), which is why VC-BLD-02 / 30 differ from both constructions; `interpolation: "linear"` (graded nodes) gives a straight contact line (9e-7) but a face area 4.3e-3 off for a law with a kink (VC-BLD-03 linear: 170.0043); a straight law without a kink (VC-BLD-17) is exact to 1e-6. Conic / curvature / asymmetric blends (VC-BLD-07 to 09) and the face blends (VC-BLD-14 to 17) are built as booleans with the corner spandrel and pass at 1e-6 relative; VC-BLD-12 / 13 (setback) and 22 (vertex names) wait for M3. See TECHNICAL_SPEC §13.5 to 13.9.

## 5. How a future implementation runs this pack

- `tests/oracle/1xx-blend-*/` — one folder per grade-A VC with `plan.json` (a slice of the plans here) and `expected.json`
  (volume / area / tolerance), as the existing oracle 83–105.
- `tests/unit/blend/*.test.ts` iterate `data/conic_sections.json`, `data/g2_sections.json`, `data/variable_radius_laws.json` for the
  core section and law math.
- `tests/golden/` imports `plans/target_*.json` once the commands exist; `plans/target_error_codes.json` runs step by step with
  `expectedCodesInOrder`.
- `server/tests/nativeBlends.test.ts` runs the baseline plans on the native kernel and records today's behaviour of
  `baseline_limits_today.json`. Measured 2026-10-22 on llull-kernel (OCCT 7.9.2), `llull run --continue`: r 6 on the 5 mm box and the two r 2 fillets on the 4 mm rib are refused with the generic "kernel could not round these edges … returned null" summary (no cause, no code: the gap FR-BLD-01 closes); chord mode on the cylinder rim is refused ("needs two planar faces … 1 planar"); the 4-edge pyramid apex at r 0.5 **succeeds** (exact B-rep, 11 faces, 23 edges), so VC-BLD-13 expects a valid solid. The other baselines: `baseline_variable_radius_laws.json` 24/24 steps ok.
